\# ADR-0009



Title: Data-Driven Combat Architecture



Status: Accepted



Date: 2026-07-16



\---



\# Context



Project KATANA contains a growing number of combat actions.



Examples include:



\- Light attacks

\- Heavy attacks

\- Sprint attacks

\- Jump attacks

\- Weapon skills

\- Boss attacks

\- Enemy attacks



Implementing every attack as dedicated code would tightly couple combat logic to individual attack implementations.



This approach would become increasingly difficult to maintain as the project grows.



\---



\# Decision



Combat actions shall be represented as data rather than hardcoded functions.



Each attack will be described by an Attack Definition containing all information required to execute it.



The AttackSystem will consume Attack Definitions and execute them generically.



Controllers coordinate execution.



Systems execute behavior.



Attack Definitions describe content.



\---



\# Consequences



Advantages:



\- New attacks require little or no engine code.

\- Weapons become data-driven.

\- Enemy attacks reuse the same execution pipeline.

\- Boss attacks reuse the same execution pipeline.

\- Combat logic becomes easier to test.

\- Designers can modify attacks without changing engine architecture.

\- Future combo systems become significantly simpler.



Tradeoffs:



\- Initial architecture requires additional planning.

\- Validation logic becomes more important.

\- Attack definitions must remain well documented.



\---



\# Alternatives Considered



\## Hardcoded Attack Functions



Example:



\- lightAttack()

\- heavyAttack()

\- sprintAttack()



Rejected because every new attack increases engine complexity.



\---



\## Object-Oriented Attack Classes



Each attack implemented as a separate class.



Rejected because it introduces unnecessary inheritance while still requiring code for every attack.



\---



\# Status



Accepted.



This decision applies to all future combat systems.
